# Reactive 核心概念复盘（D1–D3 + 端到端实测）

> 整理于 2026-11-22。所有数字都来自本仓库真实的链上执行，不是文档抄写。

---

## 一、心智模型：Reactive 到底替换了什么

传统做法：

```
你的服务器（7×24） + RPC + 监听循环 + 私钥 + 发交易脚本
```

Reactive 做法：

```
源链日志  ──订阅匹配──▶  Lasna 上的 react()  ──回调请求──▶  目标链的一笔交易
```

**替换掉的是「服务器 + 私钥托管 + 监听循环」这三样。** 你的判断逻辑变成一段跑在 Lasna（一条普通 EVM 链）上的 Solidity，规则公开可验证。

三个必须记住的位置：

| 位置 | 是什么 | 谁付钱 |
|---|---|---|
| 源链事件 | 别人合约 emit 的日志 | 事件发射方 |
| Lasna `react()` | 你写的判断逻辑 | 你的合约（lREACT） |
| 目标链回调 | Callback Proxy 代你发的交易 | **回调合约**（目标链原生币） |

## 二、订阅：最容易被误解的一层

### 它只做「等值匹配」，不是过滤器

```
subscribe(chainId, contract, topic0, topic1, topic2, topic3)
```

六个位置，每个只能填**一个确定的值**或者通配符：

| 通配符 | 含义 |
|---|---|
| `chainId = 0` | 任意链 |
| `contract = address(0)` | 任意合约 |
| `topic = REACTIVE_IGNORE` | 该位置任意 |

**没有「大于」「包含」「前缀」这类条件。** 所以：

> 「单笔超过 1000 才动作」这种判断，**永远不可能写在订阅里**，只能在 `react()` 里做。

这条决定了你所有合约的基本形状：**订阅负责「粗筛」（省钱），react() 负责「精筛」（做事）**。

### 通配的代价是钱，不是性能

D3 里我没照搬 Xfers 示例，就是因为这一条：

```solidity
// Xfers 示例的写法：通配所有合约
SYSTEM.subscribe(SEPOLIA, address(0), TRANSFER_TOPIC0, IGNORE, IGNORE, IGNORE);
```

`address(0)` 意味着 **Sepolia 上任何 ERC-20 的任何转账都会唤醒你**。每条通知收一次费（约 0.018 lREACT），几分钟就能把余额烧光。

我的改法是精确到代币地址。**订阅宽度 = 花钱速度**，这是 Reactive 里最重要的成本直觉。

### 两个静默失败的坑

1. **`unsubscribe` 的参数必须和 `subscribe` 完全一致**，差一个值就静默失败——不报错，但订阅还在，继续扣钱。
2. **订阅存在节点里，合约读不回来**。你没法在链上查询「我现在订阅了什么」，只能自己记账。

## 三、费用：一个公式 + 三个数

### 公式

```
fee = p_base × C × (g_used + K)
```

| 符号 | 含义 | 你的实测值 |
|---|---|---|
| `p_base` | `max(tx.gasprice, block.basefee)` | 100 gwei |
| `C` | `_gasPriceCoeffPer1000 / 1000` | 1.0（Lasna）/ 1.1（Sepolia 回调） |
| `g_used` | **react() 函数体**消耗的 gas | 81,262 |
| `K` | `_extraGas`（固定附加） | 100,000（Lasna）/ 150,000（Sepolia 回调） |

### 最容易忽略的一点：系统开销不收费

你 11/13 那笔 react()：

```
整笔交易 gasUsed   141,051
实际计费 gas        81,262   ← 差 59,789
```

差的这 59,789 gas 是系统合约自己的开销（订阅匹配、写日志、扣款结算），**不收你的钱**。

所以优化方向很明确：**只优化你 `react()` 函数体里的代码**，别管外面。

### 三个数：钱存在哪

| 数 | 谁持有 | 能不能挪作他用 |
|---|---|---|
| **balance** | 合约自己 | 能（合约想怎么用都行） |
| **reserves** | 系统合约代持 | **不能**，只能抵手续费 |
| **debt** | 系统合约记账 | — 这是欠款 |

规则：

```
被收费：先扣 reserves → 扣光了才产生 debt
充值：  先清 debt → 剩余才进 reserves
直接转账给合约：只涨 balance，既不算 reserves 也不抵 debt
```

所以 contract 部署时 `new X{value: 0.3 ether}(...)` 那 0.3 **只是 balance**，reserves 是 0。

### 为什么「一点 debt 就死」

系统合约处理通知走 `trigger()` 六步，**debt 检查在第一步、花任何 gas 之前**：

```
① debt > 0 ? → 直接返回，什么都不做
② 匹配订阅
③ 执行 react()
④ …
⑤ 按实际 gas 扣费
⑥ 结余给验证者
```

两个后果：

1. 判定是 **`> 0`**，不是「欠很多」。差 1 wei 和欠 1 ETH 一样死。
2. **死得静默**。因为提前返回，`react()` 根本不会被调用——不报错、不发交易、链上什么都看不到。

**这就是为什么「盯 debt」比「盯余额」更重要。**

### revert 也收费

- `react()` revert → 被 catch，记 `ReactiveContractReverted`，**全额收费**
- 回调失败 → 记 `CallbackFailure`，**全额收费**
- 唯一例外：回调目标是没代码的地址，付款前就拒绝

设计含义：过滤器一律用 `return`。而且**不能指望「出错不收费」当兜底**——逻辑有 bug 会一边烧钱一边失效。

### 测试网的「免费」是假象

你那次回调只花了约 `1e-11 ETH`，因为 Sepolia 的 baseFee 才 **15 wei**。同样的计费 gas 搬到主网（baseFee 几十 gwei），费用放大 **9~10 个数量级**。

**别用测试网的手感去估主网成本。**

## 四、安全：三道锁，缺一道都能被套钱

| 锁 | 加在哪 | 防什么 |
|---|---|---|
| `onlySystem` | `react()` | 任何人伪造日志把你叫起来，每次花你的 lREACT |
| `onlyServiceProvider` | 回调函数 | 绕过 Proxy 直接调你的回调合约 |
| `onlyCallbackSender(reactive_)` | 回调函数 | 冒充某个 Reactive 合约给你发回调 |

### payload 首参必须是 `address(0)` 占位

```solidity
abi.encodeWithSignature("onEvent(address,uint256,...)", address(0), ...);
//                                              ↑ 网络会替换成真实的 Reactive 合约地址
```

这个占位符是 `onlyCallbackSender` 能工作的前提。填错 = 回调永远鉴权失败。

### 两个不可逆

- `_CALLBACK_SENDER` 是 **immutable**，填错只能重新部署。
- **一个合约不能既是 Reactive 合约又是回调合约**。两种身份的资金来源和鉴权模型不同。

## 五、地址与链：两个认知纠偏

**① 钱包地址与链无关**（你早期卡过这个）

```
1 私钥 → 1 公钥 → 1 地址，在 Sepolia / Lasna / Base / 主网 全都一样
```

变的只是每条链上各自独立的余额。

**② 合约地址也与链无关**（D3 遇到的困惑）

```
合约地址 = keccak256(rlp(发起者, nonce))
```

只看 `(发起者, nonce)`，不看链。所以：

```
Lasna   TransferMonitor  0xd9Fb…1aD80   ← nonce=2 部署
Sepolia CampCallback     0xd9Fb…1aD80   ← 也是 nonce=2 部署
```

**同一个地址，两条链上两个完全不同的合约。** 这也解释了为什么同一人跨链部署的第一个合约地址总相同。

⚠️ 由此得出一条纪律：**任何操作都要显式指定链/RPC，永远不要依赖"默认"**。

## 六、性能：锅不在 Reactive

实测数据（你两次独立测量）：

| 分段 | 耗时 | 瓶颈在哪 |
|---|---|---|
| 源链事件块 → Lasna react 块 | **0~1 秒** | 无 |
| Lasna react → 目标链回调块 | **12 秒** | Sepolia 出块 12s |
| **端到端** | **12 秒** | **目标链出块时间** |

排期参考：

| 目标链 | 出块 | 端到端预期 |
|---|---|---|
| Sepolia | 12 s | 12 s |
| Unichain Sepolia | 1 s | ≈1 s |
| **Base Sepolia** | **200 ms** | **≈0.2–1 s** |

**结论：想赢赛道 1（Every Second Counts），把目标链换到 Base Sepolia，而不是优化 Solidity。**

配套纪律：Base Sepolia 200ms 出块，**计时、冷却、截止时间一律用时间戳，不用块高**（黑客松规则明确要求）。

## 七、如果你只能记 6 条

1. **订阅只做等值匹配**，金额/阈值判断全在 `react()` 里。
2. **订阅宽度 = 花钱速度**，`address(0)` 通配是烧钱陷阱。
3. **`debt > 0` 就静默死亡**，检查发生在花 gas 之前，不报错。
4. **revert 也收费** → 过滤器用 `return`，条件判断尽早返回。
5. **回调由接收方付钱**，proxy 参数逐链不同，目标链合约必须自己带 ETH。
6. **延迟瓶颈在目标链出块**，不在 Reactive。

## 八、自测题（答不上来就回去看对应章节）

1. 为什么「单笔转账超过 1000 才动作」不能写在订阅条件里？
2. 一个合约收到 100 条通知，其中 90 条被阈值过滤掉了，它花了几条的钱？
3. 合约 balance 还有 0.5 lREACT，但 debt 是 1 wei，`react()` 会被调用吗？为什么？
4. `react()` 里写 `revert` 和写 `return` 都能过滤事件，哪个更便宜？为什么？
5. 回调合约的构造函数填错了 reactive 地址，能不能改？为什么？
6. 同一地址在 Sepolia 和 Lasna 上都有合约，它们是不是同一个合约？
7. 端到端 12 秒，Reactive 占多少？该优化哪一段？

<details>
<summary>答案</summary>

1. 订阅只支持等值匹配，没有「大于」这种比较。
2. **100 条的钱**。过滤发生在 `react()` 里，通知已经送达、已经执行，全部计费。`return` 只是让后面的逻辑不执行，不能免单。
3. **不会**。debt 检查在第一步、花 gas 之前，判定条件就是 `> 0`。而且不会报错——静默停摆。
4. **`return`**。`revert` 会被 catch 并全额计费，`return` 尽早返回可以少执行后续代码，少花 gas。
5. **不能**。`_CALLBACK_SENDER` 是 immutable，只能重新部署。
6. **不是**。合约地址只看 `(发起者, nonce)`，与链无关，所以同地址可能是两条链上两个不同的合约。
7. Reactive 只占 **0~1 秒**，其余约 11 秒是 Sepolia 出块时间。该优化的是「换目标链」，不是改代码。

</details>
